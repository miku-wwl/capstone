2. 新证据、局限和设计决定

P13｜Tang 等（2022）｜应用层事务会改变协调范围
• 作者从 8 个流行开源 Web 应用识别并分析了 91 个应用自行协调的事务实例，归类使用方式与正确性问题。53 个实例涉及正确性问题，其中 33 个获开发者确认。选定真实 API 的实验比较了同步原语、协调粒度与回滚策略，发现应用语义有时可减少高竞争下的协调开销。
• 这两组观察同时成立：更细的协调有性能潜力，但版本验证与实际写入分离、协调漏掉业务操作或故障恢复不完整，都可能破坏正确性。开源样本和选定 API 不构成金融 API 的故障率估计。作者未对持久 HTTP 请求键与应用版本校验做本项目所问的交叉干预。依据为摘要、§§3–5、§8。
• 设计决定。A–D 均保留相同的事务、业务谓词与行锁。B/D 让版本谓词进入实际 UPDATE，同一事务完成两侧余额、转账及分录写入。用 T3、T8、T9 验证回滚与重试边界，并分别记录额外版本读取、等待、中止、重试。这将检验策略的增量效果。作者 2024 年期刊版本说明沿用了 91 个实例的研究，作为同一研究的相关版本识别，未另加到 16 篇计数。

P14｜Qi、Liu 与 Jin（2023）｜Halfmoon 将重放语义与记录成本同时衡量
• 两套非对称日志协议分别消除读取或写入一侧的日志记录，通过持久顺序与稳定逻辑时间恢复执行。在其确定性函数及共享日志假设下，研究对比 Boki，并用微基准、旅行预订、影评和 Retwis 测量端到端性能、尾延迟及记录开销。§6 还区分有相应保证的对照和不记录日志的性能下界。
• 依赖故障后重执行的 Serverless 运行时、Boki 日志及 DynamoDB。读写比例和缓存影响结果。持久函数操作记录与客户端可重放的 HTTP 响应是两个边界，论文的延迟或日志开销增益不能作为 PostgreSQL 请求键的预期值。依据为 §§2–4、6（尤其 §6.2–6.3）。
• 设计决定。Halfmoon 单列保证不同的下界，提示比较时须交代每组的保障。四组始终保留共同数据库事务，A 采用安全相对更新，W5 的旧值覆盖只用于诊断。C/D 的键、财务效果、账本和可重放结果同一事务提交，分别测量首次占键、同键等待、重放与重新执行的成本。W2 对应并发同键，W4 对应已确认提交后的 HTTP 丢失。

P15｜Cui 等（2025）｜WriteCheck 说明判定依据需要独立于被测路径
• 研究对六种 DBMS 中收集的 35 个已知关键事务缺陷做经验分析。作者以写相关可串行性（WSS）比较并发轨迹与受约束串行轨迹的最终状态，并通过可控的小范围事务调度评估 WriteCheck。§6.2 将 101 次观察到的 WSS 违反归为 22 个不同违反，其中 11 个被确认为新的关键事务缺陷。计数区分观察实例、不同问题和已确认缺陷。依据为 §§2–3、5、6.2。
• 数据库引擎缺陷的样本与判定标准不同于应用的资金不变量。READ COMMITTED 容许一些不满足通用可串行性的执行，本研究不套用 WSS 判定正常数据库行为。只比较最终余额还会漏掉守恒但重复的扣款，或同一余额对应的客户端确认错误。
• 设计决定。通过屏障控制 T1、T3、T4、T8 等关键交错。由独立 Ledger Auditor 用初始数据、独立请求记录、已提交转账、分录及客户端事件复算。分别检查每个账户、单笔借贷和每个逻辑请求的效果次数。把错误症状发生次数、受影响逻辑请求数和原因未定事件分开报告。

P16｜Zhao 等（2025）｜RTSFaaS 已包含银行转账及 OCC 对照
• 论文用亲和性租约与 RDMA 协调有状态函数，在 TiKV 与本地缓存上测量与 Boki、Beldi 的差异。评估工作负载包括电影评论、旅行预订及 Banking Service，后者通过独立借记与贷记函数模拟转账。§5.3 还将对照协议移到 RDMA 环境，检查网络条件下的协调成本。§4.3 指出提前解析依赖读取和单一租约持有者在热点处的成本。
• 端到端对比同时涉及工作流执行、存储、网络、批处理与协调协议。迁移部分协议后仍有系统语义差异。银行工作负载和 OCC 对照已经是直接相关的先例，但论文 §§4.3、5.1–5.3 所示实验未把 PostgreSQL 上的应用版本谓词、持久 HTTP 键和两类重复投递作为独立因子。该论文的输入请求率和延迟不能等同于本研究经独立对账的正确确认逻辑吞吐。
• 设计决定。固定数据库、硬件、负载初态和数据分布。除 TPS、P95 外，记录等待、冲突和重试放大，以便解释整体策略成本。采用同一后台负载与配对 seed 比较 W2/W4，明确是完整场景间交互差，不把差异单独归因于网络位置。

3. 综合判断与研究问题

Tang 表明利用应用语义可能降低竞争开销，但验证与写入边界更容易出错。RTSFaaS 表明换协调机制可改变同一种转账负载的吞吐和长尾，但组件与开销同时变动时，不能归因于应用版本谓词。Halfmoon 证明按指定规则为重放保留持久信息可以减少运行时的日志成本，同时凸显保证需依赖工作负载和执行边界。Cui 将最终状态作为独立判据的做法补足了只看等待、TPS 或 HTTP 2xx 的盲点。结合 v1.2 的 de Heus、Flux、Histrio、DBOS 与 RIFL，可知转账场景、重复执行、完成记录与恢复机制均有实质先例。

在上述有限工作清单及已核对章节中，尚未识别出同时满足以下条件的经验比较：共享正确的 PostgreSQL READ COMMITTED 单库转账基线，分别操纵应用版本验证和持久 HTTP 请求键，并在低/高竞争、并发同键与提交后 HTTP 响应丢失下同时审计财务效果及正确确认的逻辑性能。研究贡献定位为一套有可解释边界的工程对照与证据，不把新颖性扩张为新算法或银行场景首次研究。

RQ1 保留，独立判据使“行级业务约束成立”和“逻辑请求只产生一次效果”分别可检验。RQ2 保留，新增研究强化把额外读、锁等待、冲突重试和键协调作为整体策略成本的理由。RQ3 保留，已查论文未直接回答两个已匹配重复投递场景中的因子交互差。三个英文原文及分析入口见同目录系统设计。当前调整是充实证据、收窄空白表述与明确观测，实验参数沿用 v1.2 候选值，待后续正式冻结。
