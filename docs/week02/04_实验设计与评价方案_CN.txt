# MSE907 Capstone Week 2

## Day 4：实验设计与评价方案

研究主题：Evaluating Data Consistency and Performance Trade-offs in Financial Transaction Systems under Concurrent and Retry-Prone Workloads

计划日期：2026-11-26
编制日期：2026-11-23（Pacific/Auckland）
状态：研究协议草案；未执行实验，未产生结果；数据库、运行时和伦理安排仍待导师确认。

### 1. 研究设计摘要

采用定量、受控、2 × 2 因子实验，研究两个应用层机制：基于版本比较的 optimistic concurrency control（OCC）和持久化请求级幂等处理。测试对象为仅使用合成数据的关系型转账 API 原型。四组共用同一业务逻辑、数据库引擎与隔离级别、表结构、机器、负载、故障注入器和测量流程；只改变 OCC 因子和请求幂等因子。

| 组别 | OCC | 请求幂等 | 解释 |
|---|---|---|---|
| A | 关闭 | 关闭 | 保留 ACID 数据库事务，但不做应用版本比较，也不对逻辑请求去重 |
| B | 开启 | 关闭 | 对账户版本作 compare-and-swap；冲突时回滚并按统一策略从头重试 |
| C | 关闭 | 开启 | 同一稳定请求键只提交一次财务效果，并重放首次完成响应 |
| D | 开启 | 开启 | 同时使用账户版本比较和事务内幂等记录 |

主要比较 OCC 与幂等性的主效应和交互效应。研究不预设哪组更快，也不承诺所选方案达到任意 TPS、延迟或错误率阈值。正确性作为一组可审计的不变量来核对，性能作为测量结果及不确定度来报告。

### 2. 对象、系统边界和临时假设

#### 2.1 原型边界

- 一个 Web API 服务、一个关系型数据库实例、一个负载生成器；候选技术栈为 ASP.NET Core 与 PostgreSQL，具体版本在实验环境冻结前记录。
- 初步计划在单台本地开发机或导师批准的隔离测试机运行；不调用生产系统、支付网络、第三方服务或云数据库，不产生真实资金和云费用。
- 所有组固定 PostgreSQL 的 READ COMMITTED 隔离级别。它不是“关闭并发控制”：数据库事务、行更新锁、约束和原子提交在四组均保留。OCC OFF 仅表示关闭本研究增加的应用版本校验和冲突重试。PostgreSQL 文档区分隔离级别行为，并说明需要重试的事务必须从头重新执行；因此本实验将数据库隔离与应用 OCC 分开记录。
- 以上为可行性假设而非导师批准。若导师要求其他关系型数据库或隔离等级，须在正式实验前修改协议、记录原因，并重新确认四组仍只差两个因子。

#### 2.2 合成数据和事务

账户余额以整数最小货币单位存储，避免浮点舍入。每条转账请求包含逻辑请求 ID、来源账户、目标账户、正金额和客户端幂等键；单一货币、来源与目标不同、不允许负余额。每次执行产生独立账本流水主键；除启用幂等的幂等记录外，不得以逻辑请求 ID 对账本或转账表施加去重唯一约束，否则会暗中改变 OFF 组。四组 schema 保持相同，幂等表可在 OFF 组为空但不得查询或写入。为确保重复效果可观测，重复请求场景的初始余额和金额要保证再次执行不会仅因余额不足而被业务拒绝。每笔成功转账在一个数据库事务中：

1. 读取来源和目标账户及其版本。
2. 检查业务约束。
3. 扣减来源余额、增加目标余额。
4. 写入一条已提交转账/账本记录。
5. 若启用幂等，在同一事务中写入请求键、规范化请求摘要、完成状态和可重放的 HTTP 状态/响应体。
6. 提交事务后才向客户端返回成功。

交易效果、幂等记录和账户变化须由同一个数据库事务原子提交。不得在数据库事务外执行不可回滚副作用。相同的转账账本、约束和 API 验证在 A–D 中保持不变。

#### 2.3 OCC 操作化定义

- OFF：事务读取账户余额，在相同事务中按读到的余额计算新值并更新余额；不检查版本是否仍等于读取时版本。数据库原子事务仍负责避免半笔转账提交。
- ON：账户行带单调递增版本。更新条件同时匹配账户 ID 和读取到的版本，成功更新后递增版本；每个预期更新必须恰好影响一行。任一账户版本过期时，整个转账事务回滚，并从读取和业务校验开始重试，禁止只重试最后一条 SQL。
- 两账户按稳定 ID 次序更新，减少与本研究变量无关的死锁。版本冲突、数据库死锁和请求级重试分开计数。OCC 重试次数上限与退避规则在试运行前冻结；耗尽后记为明确的冲突失败，不丢弃该请求。
- 版本校验是本实验所指的应用层 OCC。不能把 PostgreSQL 的 MVCC、事务原子性或 READ COMMITTED 描述为“关闭”。达到预先冻结的 OCC 重试上限后，原型返回 409 并确认该逻辑请求没有提交；这是本原型契约，不表示 PostgreSQL 或通用 HTTP 标准要求此状态码。数据库死锁及其他非版本错误在四组执行相同错误策略，主实验不将其自动重试为 OCC 冲突。

#### 2.4 请求幂等操作化定义

- OFF：不创建或查询去重键，也不以唯一约束阻止相同逻辑请求再次产生效果。仅在测试日志保留逻辑 ID，以便审计；该 ID 不参与执行路径。
- ON：键作用域固定为单一合成 API 租户，使用数据库唯一约束保护稳定幂等键。规范化 payload 由来源账户、目标账户、金额（最小单位）和币种组成；序列化规则与摘要算法在代码冻结时记录。键记录、转账账本和余额变化在一个事务中提交。已完成的相同键、相同规范化 payload 返回首次保存的状态码和响应体，不重复记账。
- 同键不同 payload 必须拒绝且不产生财务效果；临时 API 契约采用 422 作为拒绝状态，并在实现冻结前核对所选 API 契约。
- 两个相同键请求同时到达时，唯一约束负责协调；后到者等待首个事务提交或回滚。若首个提交，则校验 payload 并重放记录结果；若首个回滚，则允许一个请求执行。等待、冲突或重放策略在 A–D 外不可变化。
- 每次重复请求均携带同一 key 和同一 payload；不同逻辑请求必须有不同 key。每个测量运行清空或重建数据，因此不在实验窗口内过期键。
- IETF Idempotency-Key 文本目前是 Internet-Draft，不是已发布 RFC；本节描述的是本研究原型契约，不宣称代表所有支付 API。

### 3. 研究变量与工作负载

#### 3.1 因子、控制变量与范围

| 类别 | 定义 |
|---|---|
| 主要处理因子 | OCC：off/on；持久化请求幂等：off/on |
| 负载因子 | 并发客户端数；热点账户请求占比；发生额外客户端重试的逻辑请求比例；故障位置 |
| 固定控制 | 业务校验、事务边界、隔离级别、数据库/运行时版本、架构、账户初值、数据分布、机器、连接池、网络路径、日志级别、负载种子、超时和重试策略 |
| 分析单位 | 一次独立运行；配对区组内四个配置使用同一负载种子和初始数据，配置执行顺序随机化 |
| 主要范围外 | 多区域一致性、真实银行业务、账本对账外部系统、支付网络、Saga、复制/故障切换、外部第三方副作用 |

#### 3.2 负载场景

Week 1 草案中的并发、热点和重试水平作为起始值保留。它们是待试运行验证的实验参数，不是文献证明的行业标准。

| 场景 | 注入方式 | 目的与观察 |
|---|---|---|
| W0 正常转账 | 唯一逻辑 ID；无重复、无响应故障；从低竞争数据分布开始 | 估计四组无故障开销及基本不变量 |
| W1 不同请求并发冲突 | 多个不同逻辑 ID 并发访问共享账户；改变热点比例 | 观察过期读、丢失更新、版本冲突、中止、吞吐和尾延迟 |
| W2 同 key 并发重复 | 两个独立客户端在同步门闩后同时提交同一 key 和同一 payload | 检查一个逻辑请求是否生成多次财务效果；观察幂等等待/重放成本 |
| W3 受控提交前超时 | 测试门闩在 API 开始数据库事务前延迟/拒绝该请求；客户端到期后以同 key 重试；日志须确认首个尝试未开始事务 | 测量已知未提交情况下的普通重试。若无法证明未开始事务，该运行改归“结果未知”，不得算成安全的提交前失败 |
| W4 提交后 HTTP 响应丢失 | 故障钩子只在数据库 COMMIT 已获服务端确认之后、HTTP 响应写出之前中止响应通道；客户端观察不到有效成功响应，随后用同 key 重试 | 核心未知 HTTP 结果场景；服务端日志和最终数据库状态用于区分“无响应”与“未提交” |
| W5 强制冲突正确性检查 | 同步两个不同逻辑转账先读取同一热点账户，再同时尝试更新；重复多个不同种子的受控轨迹 | 以确定性读后写冲突验证 OCC 定义及财务对账；只作正确性证据，不单独外推性能 |

W3 和 W4 不合并。W3 只有在事务尚未开始时才是“已知未提交”；W4 明确是在数据库已提交后丢弃 HTTP 响应。数据库 COMMIT acknowledgement 本身丢失属于第三种故障，因数据库驱动可能无法知道提交结果，且需要独立的数据库连接故障注入与恢复审计，本研究不纳入主实验。其现实意义在 Day 3 已记录；若导师要求该范围，应作为单独扩展协议重新评估，不能把 W4 的结果当作 W3 或 COMMIT acknowledgement 结果。

#### 3.3 起始参数矩阵

| 参数 | Week 1 起始水平 | 操作化说明 |
|---|---|---|
| 并发客户端数 | 1、10、25、50 | 每个客户端维持相同的请求调度规则；记录实际并发和排队 |
| 热点账户请求比例 | 10%、50%、90% | 其余请求从非热点账户均匀抽取；热点账户池大小及倾斜分布在元数据中写明 |
| 额外重试逻辑请求比例 | 0%、10%、30% | 比例的分母是唯一逻辑请求；每个被选逻辑请求只额外发送一次相同 key/payload 的请求 |
| 正确性轨迹 | Week 1 初始值 10,000 个逻辑请求 | 先在试运行核实运行时长、故障覆盖和完整账本核对；任何调整须在正式数据前冻结 |
| 每个测量窗口 | 试运行起始 60 秒 | 该值仅为工程起点；需确认负载与测量稳定性，不作为验收阈值 |

为控制组合规模，W1 在 4 个客户端水平 × 3 个热点水平 × 4 个配置下形成性能主矩阵，不叠加客户端重试。W2–W4 在试运行选定的一个稳定高冲突负载下单独改变 0%、10%、30% 重试比例和故障类型；该负载在读取正式结果前冻结。W0 作为低冲突基线。W5 仅作正确性检查。若试运行显示生成器或数据库先于被测服务饱和，降低目标负载并记录依据，不在看到正式比较结果后挑选有利水平。

### 4. 测量指标及判定规则

#### 4.1 正确性

| 指标 | 定义/审计来源 |
|---|---|
| 账本与余额对账失败 | 对每个账户，最终余额是否等于初始余额 + 已提交贷方 - 已提交借方；同时核对全体余额总和 |
| 重复财务效果 | 对发生重试的逻辑 ID，已提交账本效果数是否大于 1；逐个报告，不只报告总体平均 |
| 丢失更新/未解释效果 | 账户实际变化是否与所有已提交账本项目相符；任一转账是否仅借记或仅贷记 |
| 负余额/无效转账 | 是否违反余额非负、金额为正、来源不等于目标等共同业务约束 |
| 客户端与服务端结果关系 | 按逻辑 ID 关联每次 HTTP 尝试、服务端事务结果、已提交账本和最终客户端观察；HTTP 5xx/timeout 不能单独当作“未提交” |
| 同键不同 payload | 期望拒绝；记录拒绝状态、账本行数和余额变化 |
| OCC 检测与恢复 | 过期版本尝试数、检测数、完整事务重试数、达到重试上限的失败数 |

“零次观察到错误”仅表示在本实验的数据量和故障模型中未观察到，不能证明错误概率为零，也不能被宣传为金融系统保证。

#### 4.2 性能与资源

- 唯一逻辑转账吞吐：测量窗口内收到最终 2xx 成功结果的唯一逻辑请求数 / 窗口秒数；重复副作用和账本不一致单独计入正确性指标，避免把错误结果折算成性能失败或漏报。
- 请求尝试吞吐：包括首次请求和所有重试的 HTTP 请求数 / 秒；不得与唯一逻辑转账 TPS 混写。
- 请求尝试延迟：每次请求从计划发送时间到 HTTP 完成/超时；另报服务端处理时间。
- 逻辑请求端到端延迟：从首次计划发送到最终有结论（成功、明确拒绝或重试上限）的时间，包含等待和重试。
- 延迟分布：每次运行分别报告 P50、P95、P99；同时报告成功与失败/超时数量，不能只看已成功请求的低延迟。
- OCC 成本与冲突率：仅在 OCC-enabled 组报告版本过期拒绝数 / OCC 事务尝试数；所有组都报告门闩/请求轨迹产生的冲突机会数及数据库死锁/其他中止。OCC-off 的版本冲突检测记为“不适用”，不能把未检测记成零竞争。另报完整事务重试尝试数及每个最终成功逻辑请求的额外事务数。
- 幂等成本：幂等键插入/冲突命中/查询数、同键等待时长和记录数。
- 成功/失败：唯一逻辑请求最终状态数、HTTP 状态类别、事务提交/回滚数及对应原因。
- 系统资源：每运行记录 API 与数据库 CPU、内存、连接数、数据库读写/事务计数、负载生成器资源使用情况。

主要性能结果为唯一逻辑 TPS 和逻辑请求 P95 延迟；P99、请求尝试吞吐、CPU、冲突/重试和成功率为次要结果。不得用单一吞吐指标代替正确性。

### 5. 实验环境与控制

正式运行前保存一份只读环境清单：机器型号/CPU 核数/内存、操作系统与电源计划、API/运行时/数据库的精确版本、容器/虚拟化信息（若使用）、PostgreSQL 隔离级别与配置、连接池、磁盘类型、数据集与 schema 版本、负载生成器版本、故障钩子配置、日志设置、时区和随机种子。四组不更改上述配置。

- API、数据库和负载生成器如在同一主机运行，应记录共置及负载生成器 CPU 占用；若有第二台机器，记录网络拓扑和 RTT，并保持全部处理组一致。
- 禁止在组间升级依赖、重建不同 schema、调整连接池或改变 CPU/容器资源。正式实验期间暂停无关编译和后台任务；无法暂停的背景负载要记录。
- 每个运行使用相同的合成数据规模、账户初始余额和负载种子。重置业务数据和幂等记录，确认起始余额和余额总和正确。
- 使用单独的干运行选择固定预热时长与窗口长度。观察启动、连接池、JIT/缓存和吞吐时间序列；一旦确定，正式运行对所有组使用同一固定时长，不按某组表现临时延长。
- 测量阶段采用负载生成器独立记录预定发送时间和实际发送时间；如果使用闭环并发客户端，应明确结果表示该客户端并发下的响应时间/吞吐，不推断固定到达率下的尾延迟。监控负载生成器未成为瓶颈。

### 6. 重复次数、随机化和运行顺序

**重复单位是完整运行/随机化区组，不是单个 HTTP 请求。** 同一运行内的请求共享数据库、缓存和调度条件，不能把数千请求当成数千个独立样本。

1. 试运行用于验证门闩、响应丢失时点、事务重试、指标收集、测量窗口和资源饱和；试运行数据不进入确认性比较。
2. 每个区组使用相同数据快照和请求种子运行 A、B、C、D，四组先后顺序按预先生成的随机序列执行；每次组运行前重置业务数据。这样将日期、后台负载和种子差异作为配对区组控制。
3. 初步目标为每个主要矩阵格至少 10 个完整区组，参照相邻 MD-ACC 论文报告的 10 次独立运行；这只是起始下限，不代表统计功效已足够。NOC-NOC 报告每个数据点 5 次、每次 60 秒，说明运行次数需结合工作负载和估计精度设计，而不能机械照搬。
4. 试运行后，基于区组差值的标准差 s 和预先确认的目标置信区间半宽 δ，按 95% 区间的精度公式估算区组数：n ≈ (t × s / δ)²；从小样本起逐步重算 t 分位数。交互效应按区组内的差中差计算。δ 必须在查看正式组间结果前决定；如果无法给出有意义的 δ 或预算不足以达到所需精度，应把比较标为探索性并报告区间，不伪称已充分检验。精度思路参照 NIST/SEMATECH 样本量指导。
5. 若随机化区组中出现 API/数据库进程意外退出、采集器损坏或已定义门闩未触发，则保存该次日志并标注为基础设施无效运行；修复后重跑整个配对区组。数据库冲突、超时、重试耗尽、5xx 和低性能属于结果，不能据此排除样本。

### 7. 统计分析计划

- 在确认性运行前冻结分析脚本、主指标、排除规则和随机种子表；保留每次运行原始数据、配置、版本和日志，不只保存汇总表。
- 对每个工作负载分别计算 A–D 区组配对差值；报告四组原始值、均值/中位数、离散程度和 95% 置信区间。
- 对连续性能结果，首选区组化 2 × 2 分析，估计 OCC 主效应、幂等主效应及 OCC × 幂等交互效应；跨工作负载合并时将工作负载与机制交互项纳入模型，不把不同失败位置先平均成单一“重试率”。
- 主要交互对比写作：D−C−B+A（对响应比/比率指标在分析前改用对数尺度，并清楚解释回到原单位的结果）。具体模型假设、残差和异常值在分析报告中检查。
- P50/P95/P99 先对每次独立运行计算，再以随机化区组为重抽样单位构建区间；不能从所有请求中抽样并忽略其共享运行条件。
- 正确性事件按逻辑请求或账户暴露量报告分子/分母和区间；若事件数为零，给出与样本量相符的上界说明，不能推断绝对无风险。账户余额对账和同键效果数同时逐运行进行确定性审计。
- 报告效应量和 95% 区间，不只报告 p 值。确认性主对比数量有限；次要探索性比较如进行多重显著性检验，使用 Holm 调整并标记其探索属性。若分布/模型假设不适配，则改用按区组重抽样的稳健区间并记录理由。
- 不设“必须快 X%”或“错误率必须小于某阈值”的成功标准。研究结论由正确性审计和精确度充分披露的比较共同支撑。

### 8. 可重复执行步骤

1. 导出并核对环境清单、代码版本、 schema 版本、配置、随机种子和故障矩阵。
2. 创建合成账户并校验总余额、业务约束和账本初始状态；记录数据快照标识。
3. 执行不计入分析的 W0/W1/W2/W3/W4/W5 试运行，验证注入点和指标链路。
4. 依据试运行冻结并记录负载参数、热身/窗口、重复数、CI 半宽目标、重试上限与所有模型设置。
5. 生成随机化完整区组顺序；四配置使用相同负载种子，运行开始前重置数据库中的业务数据。
6. 每次运行按协议预热、测量、导出客户端和服务端结果；运行完成后执行余额/账本/请求键离线对账。
7. 以只读方式保存原始结果和已生成校验和；任何文件格式变换均保留脚本。
8. 在分析脚本中生成每运行指标、组间对比、置信区间和异常记录；解释任何被标为无效的基础设施运行。
9. 汇报所有预定矩阵格；若范围缩减，记录原因，区分预先调整与看到结果后的调整。

### 9. 伦理、安全与有效性威胁

#### 伦理和数据边界

- 只生成随机合成账户、金额、请求 ID；不导入个人数据、真实客户数据、真实账务或认证凭据。
- 不连接支付平台、真实账户或生产数据库；无外部资金和云费用。
- 不招募人类参与者。若导师要求使用日志、真实数据或人员测试，须先按学校流程确认伦理审批。
- 不构造真实攻击流量或对第三方服务注入故障。故障钩子仅运行于本地隔离原型。
- 研究主题、代码复用、存储期限和 AI 使用披露仍按导师及学校要求待确认。

#### 有效性威胁

- **内部效度：**本地调度、缓存、连接池、JIT、机器背景负载可能影响测量。使用冻结环境、完整随机化区组、配对种子和资源日志降低影响。
- **构念效度：**版本列 CAS 只代表明确定义的应用 OCC；稳定 key 只代表数据库事务内的请求级幂等。流处理 exactly-once、外部支付去重和跨区域 key 作用域不在测试结论内。
- **故障模型效度：**测试钩子能够精确模拟 COMMIT 已确认而 HTTP 响应丢失，但不覆盖真实 WAN 中断、进程崩溃、磁盘损坏或数据库提交确认丢失。报告须写明这个差异。
- **外部效度：**单机、单数据库、一个 API 和合成转账负载不能代表所有银行、支付服务商、硬件、分布式拓扑或生产吞吐。
- **结论效度：**请求数不等于独立运行数；样本不足、重尾延迟和多重比较会放大不确定性。以完整运行/区组为重抽样单位，公开原始观测及精度，避免过度声称。
