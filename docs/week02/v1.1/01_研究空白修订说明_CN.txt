MSE907 Capstone — v1.1 Research Gap 修订说明
编制日期：2026-11-23
定位：受限范围内的研究论证，不主张全球新颖性。

1. 从宽泛主张改为可审计主张

不再使用：“金融 API 幂等请求及重试尚未被研究”“OCC 与幂等键首次结合”等表述。

可辩护的问题是：在本次筛查的 19 项候选和针对性检索范围内，尚未找到同行评审的控制实证研究，能在具有正确数据库事务语义的 PostgreSQL READ COMMITTED 单库转账 API 中，将应用版本验证与持久化请求键作为 2×2 因子，并在不同竞争度、并发同键重复及提交后 HTTP 响应丢失下，统一测量财务不变量、正确确认吞吐、尾延迟和区组级交互效应。

这是一项有限语料与检索日期下的“尚未找到”。它不是证明不存在，也不是方法或技术新发明的主张。

2. 已知什么

- 数据库并发控制研究已经比较 OCC、混合锁、事务重试、吞吐和尾延迟（Huang et al., 2022; Chen et al., 2022; Ye et al., 2023; Kanimozhi et al., 2026）。
- Retry transparency 和应用级幂等错误已在 serverless 应用中分析与检测（Ding et al., 2023）。
- 带账户转账场景的数据流事务研究已讨论提交/消息 acknowledgement 边界和重复处理（de Heus et al., 2022）。
- Styx、Histrio 等提供事务型函数/Actor 的 exactly-once 内部消息或 side-effect 语义；其保证依赖明确运行时边界、数据库 inbox、任务恢复或外部服务幂等能力（Psarakis et al., 2025; De Martini et al., 2026）。
- DBOS 将数据库日志/事务和 workflow step 记录结合，论述可恢复工作流（Stonebraker et al., 2026）；RIFL 更早地展示持久完成记录可使重试 RPC 返回既有结果（Lee et al., 2015）。
- HTTP Idempotency-Key 已有工作中的 IETF 草案；厂商也公布了 API 实践。协议存在本身不是研究空白。

3. 尚未充分测量什么

窄问题并非“能否去重”，而是下列同一系统模型内的策略评估是否值得做：
- OFF 策略保留 PostgreSQL ACID、行锁和安全相对更新，不人为破坏 lost update。
- ON 策略增加应用侧账户版本比较与整笔事务重试。
- 第二因子为持久请求键及财务效果/结果同一事务记录。
- 竞争负载和同 key 请求/HTTP 响应丢失按可复现的预分配工况运行。
- 正确性与吞吐定义分离，并对真实成功、重复效果、响应不确定状态进行账本审计。
- RQ3 仅估计 W2 与 W4 两套场景策略的交互对比，不把时序差异说成单一网络位置的因果效应。

4. 本研究补充什么

如果导师批准且原型成功实现，本研究可提供一个可复现的教学/工程原型协议、SQL/事务边界、审计指标和受限 benchmark 结果，帮助工程团队先判断是否需要应用层版本校验与请求级幂等，再看两者在特定工作负载的增量成本。结果只适用于单服务、单 PostgreSQL 实例、READ COMMITTED、合成双账户转账和所选重试/故障模型。

5. 不试图证明什么

- 不证明 OCC 必然优于或劣于不加应用版本比较的事务策略。
- 不证明 PostgreSQL READ COMMITTED 的普通数据库并发控制被关闭。
- 不证明通用 exactly-once 或“恰好一次 HTTP 投递”。
- 不估计真实支付平台/银行的生产吞吐或故障概率。
- 不覆盖多地区、消息中间件、外部支付副作用、丢失数据库 COMMIT acknowledgement、真实用户或真实资金。
- 不以一个有限检索集合证明论文全球不存在。
- 不宣称学生研究已获得导师批准、伦理豁免或软件实现成功。

6. 对工程决策的可用结果

工程团队可按结果判断：(a) 没有幂等 key 时，同一逻辑请求重发产生重复效果的暴露；(b) 增加数据库原子持久 key 的正确性收益与重复回放/锁等待成本；(c) 应用 OCC 在其热点负载中的版本冲突、整笔重试与正确确认吞吐成本；(d) OCC 是否改变 key-enabled 策略在不同故障路径中的交互；(e) 热点/并发参数下是否应采用统一的锁顺序、retry 预算、key TTL、监控和 reconciliation。工程含义基于实测结果，不预先选定获胜方案。
