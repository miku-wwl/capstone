Histrio (De Martini et al., 2026), DOI 10.1016/j.is.2026.102724 | Lambda、DynamoDB 与 AmazonMQ 的 Actor/inbox 处理步骤；Actor 状态、收件箱与副作用同一数据库事务 | Worker crash、消息重复/遗漏、临时网络/通知失败；不等同于客户端 HTTP 响应丢失或外部响应链路 | Inbox/message identity 去重，按发送者 FIFO；不是通用客户端 Idempotency-Key + payload fingerprint | Actor 串行执行及条件操作/数据库事务 | 银行应用及其他 serverless 场景；银行例约 10,000 请求、200 账户、5 次运行 | Exactly-once message effects；银行场景 median/p90 latency | exactly-once 仅在进入 Histrio inbox 后的内部消息/side-effect 边界成立；未证明外部 HTTP response 交付 | 直接相关银行/重试先例，要求把 gap 收窄到普通关系型 API 边界及 OCC×key 组合的受控比较

RIFL, Lee et al. Plor, Chen et al. (SIGMOD 2022), DOI 10.1145/3514221.3517879 | 主存事务引擎内事务执行/提交 | 冲突导致等待或 abort/retry；无客户端请求投递故障 | 无 API 幂等键机制 | 混合 optimistic read 与 pessimistic locking，延迟冲突决策 | YCSB/TPC-C 类不同热点/事务模式 | throughput、99.9th latency、abort/wait 表现 | 论文报告特定 workload 下尾延迟收益；不能推出 PostgreSQL READ COMMITTED API 的赢家 | 支持区分数据库冲突重试、锁等待与客户端重放；不测 key
Zhang et al. (2023 issue), quantitative contention generation, DOI 10.1007/s11704-022-1056-2 | OLTP benchmark workload construction | 无主要恢复/HTTP故障模型 | 不涉及 request idempotency | 用可量化强度构造数据库竞争负载 | OLTP 竞争分布/强度 | 竞争度控制与 benchmark 可比性 | 仅核实书目与摘要；本次未读全文，支持“应量化而非仅说 high contention”的方向，不支持其技术细节 | 本研究仅借其问题意识；p_hot 不是论文算法的同义词，需实际记录 lock wait/conflict

5. 文献支撑的 gap 与边界

近期研究已经覆盖：账户转账与消息确认边界（de Heus）；serverless 并发重试幂等性及缺陷验证（Flux）；serverless Actor inbox exactly-once 与银行 workload（Histrio）；数据库 durable workflow 的步骤执行记录与恢复（DBOS）；事务级 OCC/等待/abort 与尾延迟（Plor、Polaris、Huang 等）；请求级持久完成记录的基础架构（RIFL，较早）；以及工程协议中 key 与 payload 的约束（IETF 草案）。

因此不能声称首次研究 OCC、幂等键、exactly-once 或金融转账。可辩护的窄 gap 是：在本轮 19 篇候选和上述定向官方/出版社检索范围内，尚未找到一项同行评审实证研究，在具备正确 PostgreSQL READ COMMITTED 事务基线的单库转账 API 中，把应用层版本验证和持久化 HTTP 请求键作为两个因素，系统比较四种组合，并在不同竞争度、并发同键交付及已提交后 HTTP 响应丢失下，同时报告业务不变量、正确确认吞吐、尾延迟及区组级交互估计。该陈述是有限范围内的“尚未找到”，不构成全球不存在证明，也需导师确认 Level 9 范围是否适当。
