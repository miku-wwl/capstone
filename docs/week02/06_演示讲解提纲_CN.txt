使用说明
本提纲对应 15 页英文演示稿，供学生自行核实、改写并练习。讲解时长与正式展示形式尚待课程要求确认。材料属于 AI-assisted internal review draft；请按学校政策披露 AI 辅助，不代表导师批准或正式提交。姓名和学号由学生本人补齐。

第 1 页｜研究主题
说明本研究拟考察金融转账 API 中的并发冲突与请求重放，重点比较应用层 OCC 与持久请求幂等性的单独效果和组合效果。强调这是研究计划，不是已完成实验。

第 2 页｜行业问题
区分两种情况：不同转账同时更新同一账户时会发生事务冲突；同一逻辑请求因客户端没有收到可用响应而被重发时可能重复产生金融效果。OCC 和幂等键处理的是不同层次的问题，底层转账原子性在各组保持不变。

第 3 页｜相邻研究证据
概括三类文献：OCC 与 OLTP 竞争、事务/函数系统中的重试语义、分布式或流处理系统中的一致性边界。说明这些研究支持选择因素与指标，但平台和工作负载不同，不能直接预测本 API 的性能。

第 4 页｜有限范围的研究空白
报告本轮记录的 19 篇候选材料、8 篇全文深读和 11 篇结构化筛查。说明在该范围内未找到直接对应的受控比较；这不是系统综述，也不是对全球文献的穷尽证明或“首创”声明。

第 5 页｜问题、目标和系统边界
说明拟使用一个合成转账 HTTP API 和一个关系型数据库，所有实验组保持相同事务边界、隔离级别、schema、业务规则和环境。ASP.NET Core、PostgreSQL 与 READ COMMITTED 仍是待导师确认的候选方案；生产数据、真实资金及数据库 COMMIT 确认丢失不在范围内。

第 6 页｜研究问题
依次说明 RQ1 关注财务不变量与重复效果，RQ2 关注吞吐、延迟、重试和资源成本，RQ3 关注 OCC 与幂等性的交互是否随故障位置而变化。

第 7 页｜机制与故障时点
沿图说明客户端提交稳定请求键和转账内容，API 在单个数据库事务内执行可选版本检查、可选幂等记录、借记、贷记、账本记录和可重放结果。W3 必须证明事务尚未启动；W4 则在数据库已报告 COMMIT 成功后丢弃 HTTP 响应。数据库 COMMIT 确认丢失属于另一故障模型。

第 8 页｜四个实验组
说明 A 为 OCC 关、幂等关；B 仅开启 OCC；C 仅开启持久请求幂等；D 同时开启两者。这里的 OCC 关只表示关闭额外的应用版本检查和相应重试，不会关闭数据库事务或隔离。

第 9 页｜工作负载与故障注入
按 W0 至 W5 说明正常基线、不同请求竞争、并发同键请求、事务前超时、提交后响应丢失以及用于确定性正确性检查的强制冲突。W3 与 W4 不合并；W5 不作为性能估计。

第 10 页｜正确性评价
说明将逐账户核对期初余额、已提交借贷和期末余额，并核对每笔已提交转账及重复效果。客户端超时或 HTTP 5xx 本身不能证明事务已回滚。

第 11 页｜性能评价
区分唯一逻辑转账吞吐与 HTTP 请求尝试吞吐。逻辑端到端延迟包括重试直到最终结果；另报告延迟分位数、事务重试、冲突、同键等待和 API/数据库资源。此阶段没有实验结果图。

第 12 页｜统计分析
独立完整运行/随机化区组才是性能样本；同一运行中的请求不能当成独立样本。四组使用相同数据快照和种子，随机化执行顺序，试运行数据不进入确认性比较；最终重复数根据试运行变异度和预先确定的区间精度目标决定。

第 13 页｜潜在贡献与伦理界限
说明若获准并完成，研究可给出一个边界清楚的 OCC × 幂等性比较，并同时核对正确性与性能。实验只使用合成账户、金额和请求键，不使用真实资金、个人数据、生产系统或人类参与者；主题及伦理路径仍待确认。

第 14 页｜十四周计划与待确认安排
按四个阶段介绍确认问题、实现原型、试运行与冻结方案、正式运行及分析修订。特别指出 Assessment 1 手册写明 Week 15 完成，而先前转述的课堂安排提到 Week 6 PPT；正式日期、PPT 时点和格式应以课程负责人确认结果为准。

第 15 页｜参考资料与来源类型
展示关键同行评审研究，并说明完整 APA 参考文献、DOI 和 URL 在配套研究计划书第 13 节。IETF Idempotency-Key 文档仍是 Internet-Draft，不是 RFC；Adyen、Square 和 PostgreSQL 文档用于实现背景，不作为同行评审比较实验。
