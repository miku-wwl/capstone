MSE907｜批判性文献综述
主题：应用层版本验证与持久请求幂等在单数据库转账 API 中的正确性和性能权衡。
阅读口径：依据已归档的定向阅读记录，不是本次重新阅读全文或系统综述。原18篇 DOI 候选加 Flux 共19篇，其中8篇有全文深读记录；Plor 后续全文核查、竞争度论文仅摘要核查。Histrio 为可访问章节，DBOS 与 RIFL 有后续全文核查记录。正式学术论证纳入原候选集10篇、Histrio/DBOS两篇近期研究及 RIFL 一篇早期基础论文。原始筛选与页节证据见 GitHub v1.0/v1.1 历史；本人应回查原文。

一、核心论文：并发控制与竞争强度

1. Huang et al. (2022)｜主存多核事务中的乐观控制
问题：OCC、MVCC 等协议的表现差异是否来自协议本身，还是实现选择？
方法：在 STO 平台比较多种事务协议及实现因素；用 TPC-C、YCSB 等负载改变竞争度、线程数，并测试延迟更新及时间戳拆分。
发现：作者在高竞争 TPC-C 中报告部分优化约2–5倍吞吐改善，说明实现选择足以改变协议比较结果。
局限：主存事务平台、特定记录语义与手工优化；没有请求键和 HTTP 故障。不能将其性能倍数当成本研究的预期结果。
启发：四组必须共享正确的数据库基线、约束和环境，才能解释增量策略成本。证据：原全文记录，期刊 pp.1239–1261。

2. Chen et al. (2022)｜Plor 与可预测尾延迟
问题：如何在通用事务中控制等待、冲突和尾延迟？
方法：结合乐观读取与悲观锁，推迟部分冲突处理决策；在 YCSB/TPC-C 类负载比较吞吐、abort/wait 和极端尾延迟。
发现：特定竞争条件下报告更低尾延迟，说明“尽早中止并重试”并非所有负载下的最佳策略。
局限：主存事务引擎，没有客户端重复投递、持久 HTTP key 或响应丢失。
启发：同时记录锁等待、重试与 P95；把版本检查及其整笔重试看成可部署策略，不声称孤立测量一个谓词。证据：后续全文记录，协议与 benchmark 章节。

3. Ye et al. (2023)｜Polaris 与事务优先级
问题：OCC 下如何减少高优先级事务的尾延迟与饥饿？
方法：在 DBx1000 引入轻量 reservation，比较 Silo OCC、2PL 等；通过线程数和 Zipf 偏斜改变 YCSB/TPC-C 子集的竞争。
发现：作者报告特定高竞争条件下高优先级事务 p999 可比低优先级低13倍；收益与优先级及负载分布相关。
局限：研究优先级协议而非普通版本字段；不处理 HTTP 重复请求。
启发：竞争影响中止和长尾，不能把内部事务重试和客户端重发混为一谈。证据：原全文记录，PACMMOD 1(1), Article 44。

4. Zhang et al. (2023)｜定量竞争负载生成
问题：怎样构造可量化的 OLTP 竞争，而非笼统描述高竞争？
方法/发现：出版摘要支持将竞争度作为可控负载问题；当前记录不足以复述其具体算法或量化结果。
局限：只核查书目及摘要；没有 HTTP 幂等研究。
启发：冻结热集合与访问概率，另外记录实际账户重叠、行锁等待和冲突率，不能把热点比例直接当成竞争率。证据：摘要级，Article 172202。

5. Kanimozhi et al. (2026)｜测量驱动的高竞争控制
问题：运行时反馈能否缓解高竞争 OLTP 的中止级联与重试放大？
方法：Java 分布式合成测试床比较 MD-ACC 与静态 OCC/2PL/MVCC 等，观测冲突、队列、重试与退避。
发现：论文报告极端竞争下最高约2.1倍吞吐改善；这是其特定测试床的结果，不是本项目结果。
局限：内存键值层、复制关闭、合成 TPC-C-inspired 负载；阅读记录指出测量窗口描述存在200ms与1–5s差异，不能借用其阈值。
启发：记录 retry amplification 与资源开销；冻结自己的 pilot 参数。证据：原全文记录，方法、结果与 validity 章节。

二、核心论文：重试、幂等及恢复边界

6. de Heus et al. (2022)｜跨 Serverless 函数的状态数据流事务
问题：怎样为多个函数及状态提供强事务或 Saga 工作流？
方法：在 Flink StateFun 加入协调函数和2PC/Saga，以扩展 YCSB 转账负载比较 Beldi、CockroachDB+Kafka 等。
发现：协调有额外成本；高竞争下 Saga 可较快，但保证较弱。作者指出数据库已执行而消息 acknowledgement 未确认时可能重放，需要应用专用幂等键。
局限：均匀键分布与 Serverless 运行时；未独立操纵应用 OCC 与持久 HTTP key。
启发：资金状态与客户端确认不是同一个事务边界；需要以同一逻辑请求关联账本。证据：原全文记录，约 pp.1–14，交易模型、讨论和结论。

7. Ding et al. (2023)｜Flux：并发 Serverless 幂等验证
问题：能否验证并发函数在重试下对客户端保持透明？
方法：提出 idempotence consistency，利用符号执行、逐函数模拟和选择性日志；评估27个应用、79个函数。
发现：作者发现12个应用中的既有问题，其中8个得到开发者确认；错误可表现为重复扣款或响应与状态不一致。
局限：Java、NoSQL 模型；验证 sound but incomplete，不等同于关系型交易 API 的 key 表策略。
启发：正确性应独立审计客户端与账本的可观测结果，不只检查 HTTP 2xx；已有幂等研究直接否定宽泛的新颖性主张。证据：原全文记录，OSDI pp.887–910。

8. Psarakis et al. (2025)｜Styx：事务型 Stateful Functions
问题：怎样为任意函数调用图实现可扩展串行化事务及 exactly-once？
方法：结合确定性事务、流式执行、确认协议、快照和输入/输出队列；测试 YCSB-T 转账及 TPC-C 子集等。
发现：所测高竞争 YCSB-T 下报告稳定执行；外部调用要求外部服务支持幂等键，并协调调用标识和重放结果。
局限：确定性应用逻辑和数据流运行时假设；外部服务幂等是前提，不是任意外部 API 的已证明性质。
启发：持久请求键及结果必须与财务效果协调，不能用数据库事务自动推导端到端 exactly-once。证据：原全文记录，架构、commit、Exactly-Once、评估。

9. De Martini et al. (2026)｜Histrio：Actor/inbox 与银行场景
问题：Serverless actor 如何协调消息、状态和副作用？
方法：Lambda、DynamoDB、AmazonMQ；利用 inbox/message identity、actor 顺序处理及事务，包含银行账户负载。
发现：exactly-once 保证针对已进入系统的消息及相应内部事务；不是外部 HTTP 响应交付保证。可访问的银行实验包含延迟测量。
局限：依据出版页、摘要及可访问第5、6.3、7节；非全文核验。Actor 模型不等价于 PostgreSQL 多账户更新和 HTTP key/fingerprint。
启发：必须承认金融与 exactly-once 已有直接先例；本研究只能聚焦不同系统边界与控制比较。

10. Stonebraker et al. (2026)｜DBOS：数据导向持久工作流
问题：怎样协调持久工作流步骤、业务状态与恢复记录？
方法：PostgreSQL 支撑的执行日志与事务/工作流机制，讨论事务型和补偿型策略并评估电商工作流。
发现：第7.1节等说明已完成步骤的记录与恢复机制；系统在不同竞争条件下存在事务与 Saga 的权衡。
局限：工作流级而非独立 HTTP 转账接口；未比较普通 API 的版本验证×客户端 key。正式会议年为2026，不使用 PDF 模板占位 DOI。
启发：持久执行记录不是新技术；转而测量不同请求边界和应用事务策略。证据：后续全文核查，CIDR 2026 官方 PDF。

11. Lee et al. (2015)｜RIFL：持久完成记录（早期基础研究）
问题：如何让 RPC 重试安全地返回既有结果而不重复执行？
方法：RAMCloud 中的 request ID、持久 completion record、重试汇合、记录回收及线性化/事务机制。
发现：请求身份和完成记录的原子协调能够支撑其模型内重试语义。
局限：分布式内存对象模型，非近期关系型金融 API 证据。
启发：请求键与结果协调已有基础先例；重点是增量成本与适用边界。证据：后续全文记录，SOSP §§3、6。

三、事务模型背景与综合判断
12. Liu et al. (2024), NOC-NOC：在分布式隔离与通信目标中给出不可兼得的边界，并评估相关算法；合成 YCSB 类负载不能替代单库金融 API。启发是明确保证与成本，而非外推其吞吐。原全文记录，Article 9。
13. Zhang, Soto & Markl (2024)：分类事务流处理的事务边界、恢复与系统架构；不同模型存在接口、同步及性能代价。这是综述，不是本研究的直接实证。启发是分别描述输入、状态和输出的原子边界。原全文记录，pp.451–479。

四、跨研究综合（工程问题｜已有证据｜本研究采用的判断）
并发控制｜Huang/Plor/Polaris/MD-ACC：实现、等待及竞争影响尾延迟｜统一数据库基础因素，观察实际竞争而非假定 OCC 一定更快。
持久幂等｜Flux/Histrio/DBOS/RIFL：请求身份、日志与结果回放已有先例｜让 key、财务效果和可重放结果协调；分别验证同键并发与异载荷。
重试恢复｜de Heus/Styx/DBOS：恢复保证受系统边界制约｜区分数据库冲突重试、客户端重复投递、已提交后 HTTP 丢失及未知数据库提交结果。
正确性与性能｜NOC-NOC/事务流综述：保证、延迟及成本存在权衡｜用账本不变量和正确确认吞吐同时评价，不以成功响应率替代正确性。

证据边界：上述作者报告的数字不是 Capstone 测量结果；直接先例改变了研究问题的表述，但不能代替本研究在安全 PostgreSQL 基线上的四组实证。文献清单见 Day01，最终 gap 与 RQ 见 Day03。官方技术依据（非学术实验）：PostgreSQL 18 https://www.postgresql.org/docs/18/transaction-iso.html；IETF Internet-Draft -09 https://datatracker.ietf.org/doc/html/draft-ietf-httpapi-idempotency-key-header-09（非 RFC）。
